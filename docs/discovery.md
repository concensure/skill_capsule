# Skill Capsule Discovery — Analysis & Proposal

## The Problem

Finding the right atom or capsule in a growing registry is a **Discovery vs. Density** tradeoff. Two failure modes:

- **Read everything**: Load all JSONs to find one atom. At 12 atoms this is fine; at 50 it's a 3,000–8,000 token tax before any real work starts.
- **Guess from filenames**: `code.edit.safe` vs `code.edit.scope_guard` — impossible to distinguish without reading both.

---

## Evaluation of the Proposed Approaches

### Approach A — Semantic Capability Map (MAP.md with Intent Domains)

Organise atoms under human-readable intent headers ("Surgical Code Modification", "Repository Integrity") in a single Markdown file.

**Strengths**
- Hierarchical reading: scan headers first, only dive into the relevant section.
- Natural language descriptions help LLMs match vague user intent.
- Zero runtime changes.

**Weaknesses**
1. **Manual maintenance creates drift.** Every new atom requires a human to choose the right domain and write a line. By atom 30 the map is stale.
2. **Domains are too coarse.** "Surgical Code Modification" covers `code.edit.safe`, `code.edit.scope_guard`, and `code.refactor.boundary_check`. The discriminating signal is *risk level* and *scope*, not the domain heading.
3. **Re-invents the trigger system.** Atoms already declare `triggers.keywords` and `triggers.task_types`. MAP.md paraphrases these in prose — lossy, redundant, and out-of-sync by default.
4. **Three hops.** INDEX.md → MAP.md → atom JSON. Each hop is a separate read.

---

### Approach B — Root Index (INDEX.md) + Domain Files

A root INDEX.md pointing to per-domain Markdown files (e.g., `skills/domains/coding.md`).

**Strengths**
- Splits the index so a single domain can be loaded without loading all others.
- Scales better than a flat list.

**Weaknesses**
1. **Still manual.** Domain files must be kept in sync with atom JSONs.
2. **Adds a directory layer** that doesn't exist in the current `atoms/` / `capsules/` structure; moves discovery logic out of the runtime's canonical source of truth.
3. **Ignores existing CLI.** `skillcap classify --task <t>` and `skillcap match --task <t>` already do intent-to-ID routing. The index approach duplicates this in static files.
4. **Doesn't scale sub-linearly.** Adding a new domain requires creating a new file, updating INDEX.md, and writing into the domain file — three write operations for one new atom.

---

### Core problem both approaches share

Both treat discovery as a documentation problem and solve it with manually written Markdown. This is the wrong layer: the atom JSON files are the source of truth, and any static file derived from them will drift.

---

## Proposed Solution — Compiled Intent Fingerprint (CIF)

### Concept

Generate a single ultra-compact routing file **automatically from the atom registry** every time `skillcap index` runs. Call it `.skillcapsule/CIF.md`. It is never hand-edited.

```
# CIF v1 — generated by `skillcap index` — do not edit
# Format: triggers → id  [capsule?]  risk  notes
edit|fix|update|patch|change → code.edit.safe  low-med
scope|cross-file|boundary|multi-module → code.refactor.boundary_check  [code.edit.safe]  med-high
review|diff|risk|danger → code.review.diff_risk  med
test|related|coverage → code.test.related_tests  low
typecheck|types|ts-error|compile → code.verify.typecheck  low  depends: none
push|upload|github → github.upload.safe  [capsule]  med  entry: github.upload.safety
commit|message|conventional → github.commit.message  low
secret|scan|leak|token → github.upload.safety  low  required-by: github.upload.safe
confirm|approval|gate → github.push.confirmation  high
usage|log|telemetry|track → meta.monitor.usage  low
propose|evolve|pattern|new-capsule → meta.propose.composite  low  dry-run
scope-guard|guard|escape|drift → code.edit.scope_guard  low-med
```

Each line is: `{pipe-separated triggers} → {atom_id}  [{parent_capsule}]  {risk}  {notes}`

The file is generated by extracting `triggers.keywords`, `triggers.task_types`, `risk_level`, and capsule membership from every atom JSON.

### Token Cost Comparison

| Approach | Tokens at 12 atoms | Tokens at 50 atoms | Tokens at 200 atoms |
|---|---|---|---|
| Load all atom JSONs | ~2,400 | ~10,000 | ~40,000 |
| MAP.md (proposed) | ~400 | ~1,200 | ~4,000 |
| INDEX.md → domain files | ~200 + ~300/domain | similar | similar |
| **CIF.md (this proposal)** | **~180** | **~600** | **~2,000** |

CIF stays roughly 10–12 tokens per atom. It is the smallest possible routing layer that still encodes discriminating signal.

### Discovery Flow

```
Session start
  └── Load CIF.md once (~180 tokens for 12 atoms)

User: "Fix the bug in index.ts"
  └── Scan CIF for "fix" → matches: code.edit.safe (low-med risk)
  └── Load only .skillcapsule/atoms/code.edit.safe.json
  └── Compose with full atom contract

User: "Upload to GitHub but do not push"
  └── Scan CIF for "upload|github" → github.upload.safe [capsule]
  └── Load .skillcapsule/capsules/github.upload.safe.capsule.json
  └── Negative intent "no_push" blocks github.push.confirmation at runtime
```

Two hops maximum: CIF → target JSON. The LLM never reads more than one atom/capsule JSON per task.

### Why CIF outperforms both proposed approaches

| Property | MAP.md | INDEX.md | CIF.md |
|---|---|---|---|
| Auto-generated | No | No | **Yes** |
| Drift-proof | No | No | **Yes** |
| Encodes actual triggers | No (paraphrase) | No (prose) | **Yes (verbatim)** |
| Distinguishes similar atoms | Weak | Weak | **Yes (risk + capsule tag)** |
| Scales sub-linearly | No | Partial | **Yes** |
| Runtime integration | None | None | **Generated by existing `skillcap index`** |
| Hops to atom JSON | 3 | 3 | **2** |
| Token cost at 50 atoms | ~1,200 | ~1,400 | **~600** |

### What CIF does not replace

CIF is a routing table, not documentation. It does not replace:
- Atom JSONs (the contract, hook bindings, render levels are all in the JSON)
- `skillcap match --task <t>` (the CLI does full semantic matching; CIF is the offline/zero-tool version)
- `docs/design.md` and `docs/architure.md` (human-facing explanation of the system)

## Implementation

### Step 1 — Add CIF emission to `skillcap index`

In `bin/skillcap.js`, extend the existing `index` command:

```js
// Existing: rebuild atom/capsule index
// Add: --emit cif flag

if (options.emitCif) {
  const lines = atoms.map(a => {
    const triggers = a.triggers.keywords.join('|');
    const capsuleTag = capsuleIndex[a.id] ? `  [${capsuleIndex[a.id]}]` : '';
    const risk = a.risk_level ?? 'unknown';
    return `${triggers} → ${a.id}${capsuleTag}  ${risk}`;
  });
  fs.writeFileSync('.skillcapsule/CIF.md',
    `# CIF v1 — generated by \`skillcap index\` — do not edit\n` +
    `# Format: triggers → id  [capsule?]  risk\n` +
    lines.join('\n') + '\n'
  );
}
```

### Step 2 — Regenerate on every `skillcap index`

Make CIF regeneration the default (not a flag). Every time an atom is added or modified, `skillcap index` refreshes CIF automatically.

### Step 3 — Pin CIF in project context

Add to `CLAUDE.md` or `.skillcapsule/skillcapsule.config.json`:

```json
"context_hints": {
  "session_start": [".skillcapsule/CIF.md"],
  "on_task_match": [".skillcapsule/atoms/{matched_id}.json"]
}
```

Or in `CLAUDE.md`:

```markdown
Before any skill operation, load `.skillcapsule/CIF.md` (one read, ~200 tokens).
Then load only the single atom JSON the CIF routes you to.
```

### Step 4 — Optional: BOOT.md for zero-token sessions

For contexts where even CIF is too much, a 3-line BOOT.md:

```markdown
# SkillCapsule Boot
Fastest path: run `skillcap match --task "<your task>"`
If offline: load .skillcapsule/CIF.md then the single atom it routes to.
```

This costs ~30 tokens and gives the LLM two paths: CLI (zero reading) or CIF (two-hop reading).

---

## Summary

The MAP.md and INDEX.md proposals are the right direction but the wrong implementation layer — manually maintained Markdown always drifts from JSON source of truth.

CIF.md solves the same problem by being **compiled, not curated**: it is regenerated from atom triggers on every `skillcap index` run, encodes the actual discriminating fields (triggers + risk + capsule membership), costs ≤12 tokens per atom, and reduces discovery to two hops regardless of registry size.

No new runtime logic is needed — only a new output format for the existing index command.
